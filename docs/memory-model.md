## 1. 왜 스택과 힙을 나눴나

스택은 태생이 **LIFO(후입선출)**. 함수 리턴 시 프레임을 통째로 자동 해제 → 청소가 공짜, SP 이동뿐이라 빠름.
그러나 이게 성립하려면 **"수명 = 스코프"** 여야 한다. 현실 데이터는 그 제약을 벗어난다.

**"전부 스택"이 깨지는 4가지** — 한 함수 프레임에 가둘 수 없는 것들:

| 사유 | 예 | 왜 스택 불가 |
|---|---|---|
| **수명 (주 이유)** | 함수가 만든 객체를 `return` / 저장 | 리턴 시 프레임 파괴 → 댕글링 |
| **크기** | 런타임에 크기 정해지거나 자라는 자료구조 (레이어 1 HashMap 100만 개) | 프레임은 컴파일타임 고정 크기 |
| **공유** | 여러 스레드가 같은 저장소 참조 (레이어 4a) | 스택은 스레드 전용 |
| **거대함** | GB 데이터 | 스택은 작고 고정(`-Xss`) |

이 넷은 결국 한 뿌리: **"이 함수 흐름 하나로 감당 안 되는 데이터"** → 힙.

**"전부 힙"도 안 되는 이유** (스택을 남겨두는 이유):
- 매 할당이 GC/매니저를 거쳐 느림, GC 압력 ↑, 캐시 지역성 ↓.
- **함수 호출 자체가 LIFO 스택을 강제**(리턴주소·저장레지스터) → 스택 없이는 call/ret 구현 불가.

→ **스택 = 흔한 경우(함수지역·단명·LIFO) 최적화 / 힙 = 일반 경우(임의 수명·크기·공유).** 서로의 약점을 메우는 분업.

| | 스택 | 힙 |
|---|---|---|
| 수명 | 스코프에 묶임(LIFO) | **임의** — 호출구조 독립 |
| 크기 | 컴파일타임 고정, 작음 | **동적, 큼** |
| 할당비용 | SP 이동(≈0) | 매니저/GC(비쌈) |
| 해제 | 리턴 시 자동 | GC/free(관리 필요) |
| 공유 | 스레드 전용 | 여러 스레드·구조가 공유 |
| 단편화 | 없음 | 있음 |

## 2. 프레임 (stack frame)

**프레임 = 함수 호출 한 번의 작업공간 한 칸.** 호출 시 push, 리턴 시 pop.

담기는 것: **리턴주소**(끝나면 돌아갈 곳, `CALL`이 자동 푸시) · 파라미터 · 지역변수 · 저장 레지스터 · 임시 계산공간.

```
높은 주소
┌─────────────┐
│ main() 프레임│  먼저 호출, 맨 아래
│ f()    프레임│
│ g()    프레임│
│ h()    프레임│  ← 지금 실행 중, 맨 위 (RSP)
└─────────────┘
낮은 주소 (스택은 아래로 자람)
```

- **스택의 프레임 더미 = 지금까지의 호출 경로 그 자체.** `jstack` 출력의 **한 줄 = 프레임 하나**.
- 생성(prologue): `CALL` 이 리턴주소 푸시 → `push rbp; mov rbp,rsp; sub rsp,N` 로 지역변수 N바이트 확보.
- 소멸(epilogue): `RSP` 되돌려 프레임 해제 → `RET` 이 리턴주소 팝. 청소 공짜.
- 프레임 크기 N = **컴파일타임 확정** (바이트코드 `Code` 속성의 `max_locals`/`max_stack`, `javap -v` 로 확인).

**JVM 프레임 3부분**: (1) 지역변수 배열(슬롯, `iload 2`) (2) 피연산자 스택(`iadd` 작업대, 깊이 `max_stack`) (3) 프레임 데이터(상수풀 참조·예외정보).

## 3. StackOverflowError — "깊이" 초과

- 스택은 `-Xss` 로 **고정**, 안 자란다. 끝에 **가드페이지**(`PROT_NONE`)가 박혀 있음.
- 프레임을 push하다 가드페이지를 밟으면 → 폴트 → JVM이 **`StackOverflowError`** 로 번역.
- **논리적 경계 위반이지 물리 메모리 부족이 아니다.** RAM이 남아돌고 스왑이 비어 있어도 `-Xss` 경계에서 **즉시** 터진다. **스와핑은 끼어들 여지 없음.**

**Java에선 사실상 재귀(또는 과도한 호출 깊이)로만 발생.**
- 프레임 크기는 작고 고정 — 지역변수엔 원시값/**참조(8B)** 만, 배열·객체 실체는 힙. `int[10_000_000]` 도 스택엔 참조 8B뿐.
- C와 결정적 차이: C는 `char buf[10MB]`·VLA·`alloca` 로 **한 함수가** 스택을 통째로 먹을 수 있음. **Java엔 그런 수단이 없음** → 프레임 개수(깊이)로만 넘침.
- 드문 비-재귀 SOE: 수천 단계 깊은 호출 체인(파서·프록시), 자동생성된 거대 단일 표현식, `-Xss` 극단적으로 작게.

**진단**: `jstack` 에 동일 프레임 수천 줄 = 재귀 폭주 증거.
**프로젝트 주의**: 레이어 6 트리(B-tree/Skip List) 재귀 삽입/순회 시 깊이 폭발 → 반복문 변환 or 깊이 제한.

## 4. OutOfMemoryError — "양" 초과 (한 종류가 아님)

SOE(깊이)와 달리 OOM은 **어느 영역이 찼는지** 메시지로 갈린다. 이걸 읽는 게 실전 진단.

| OOM 메시지 | 영역 | 원인 | 처방 | 이 프로젝트 |
|---|---|---|---|---|
| `Java heap space` | **힙** | 객체 과다/누수 | `-Xmx`↑ or 누수 잡기 | 레이어 1~5, 캐시·컬렉션 누수 |
| `GC overhead limit exceeded` | 힙 | GC 98%인데 회수 거의 0 | 위와 동일 | 힙 꽉 참 전조 |
| `unable to create new native thread` | **네이티브** | 스레드수 × 스택 > 한계 | **`-Xmx`↓**(네이티브 여유) or 스레드 줄이기 | **레이어 4a 스레드폭발** |
| `Metaspace` | **메타스페이스** | 클래스 메타 과다(로더 누수) | `MaxMetaspaceSize`, 로더 점검 | 리플렉션·동적클래스 |
| `Direct buffer memory` | **off-heap** | direct buffer 안 풀어 누수 | 풀 재사용, 상한 점검 | **레이어 2/4b** NIO 버퍼 |

**핵심 통찰 — "힙은 멀쩡한데 OOM"**:
- 힙 계열: `jmap -histo`/힙덤프로 진단, `-Xmx`↑.
- 네이티브 계열(thread/direct): **힙 도구로 안 잡힘** → `jcmd <pid> VM.native_memory summary`(NMT). `-Xmx`↑는 오히려 역효과(전체 RAM 유한). 레이어 4a에서 "histo 깨끗한데 왜 죽지?"의 답.

## 5. SOE vs OOM vs OOM Killer — 누가 던지나

**SOE·OOM 둘 다 JVM이 던진다.** OS는 Java 예외를 못 만듦(Java 타입을 모름). 다만 "자원 없음" 신호가 어디서 오느냐가 다르고, **진짜 호스트가 죽이는 건 별개**다.

| | 한계 주인 | 거절 감지 | 던지는 주체 |
|---|---|---|---|
| StackOverflowError | JVM(`-Xss`) | OS/CPU 가드페이지 폴트 | JVM이 번역 |
| OOM `Java heap space` | JVM(`-Xmx`) | **JVM 자신**(GC해도 자리 없음) | JVM (OS 무관) |
| OOM `native thread` | **OS** | **OS**가 syscall 거절(ENOMEM) | JVM이 번역 |

**Linux OOM Killer (진짜 OS 레벨 살해 — Java 에러 아님)**:
- 시스템 **전체** RAM+스왑 고갈 → 커널이 프로세스를 골라 **`SIGKILL`(9)** 로 즉살.
- **스택트레이스 없음, catch 불가, finally 안 돎.** JVM이 통째로 증발. 흔적은 `dmesg`/`journalctl` 의 `Out of memory: Killed process`.
- **컨테이너 함정**: Docker/K8s 메모리 리밋 초과 시 자주 발동 → JVM이 아무 에러 없이 "그냥 사라짐". `-Xmx` 를 컨테이너 리밋보다 크게 잡으면 힙 OOM(Java) 뜨기 전에 커널이 먼저 죽임 → **`-Xmx` 는 리밋보다 작게**(또는 `-XX:MaxRAMPercentage`). 레이어 4~5 이후 배포 때 꼭 만남.

## 6. 할당 메커니즘 — syscall은 언제만 일어나나

**핵심: 개별 할당(프레임 push / 객체 new)은 syscall이 아니다.** syscall은 **영역을 처음 잡거나 늘릴 때만.**

| | 영역 확보(1회성) | 개별 할당(매번) |
|---|---|---|
| 스택 | 스레드 생성 시 `mmap` (1회) | **SP 레지스터 이동**, syscall X |
| 힙 | JVM 시작 시 `mmap` reserve/commit | **TLAB 포인터 bump**, syscall X |

- **TLAB(Thread-Local Allocation Buffer)**: 스레드마다 힙 조각을 받아두고 `new` = 포인터 증가. 락도 syscall도 없음 → `new` 가 C `malloc` 보다 빠를 수 있는 이유(bump < free-list 탐색).
- **Java `new` 가 어디로 갈지 결정하는 syscall도 없다** — 스택/힙 구분은 **컴파일타임**에 이미 결정(→ §7).

**OS별 영역 syscall**:

| 목적 | Linux | Windows |
|---|---|---|
| 예약/커밋 | `mmap` / `mprotect` | `VirtualAlloc(MEM_RESERVE/COMMIT)` |
| 반납 | `munmap` / `madvise(DONTNEED)` | `VirtualFree` |
| C 힙 확장 | `brk`/`sbrk` | `HeapAlloc`(내부 VirtualAlloc) |
| 스레드 스택 | `pthread_create`→`mmap` | `CreateThread(stackSize)` |
| 가드페이지 | `mprotect PROT_NONE` | `PAGE_GUARD` |

**프로세스 시작 타임라인** (`java Main`):
1. **커널 `execve`**: 코드/데이터/bss 매핑 + **메인 스레드 스택**(커널 자동, mmap 아님) + program break(빈 C 힙).
2. **JVM 초기화**: 여기서 **명시적 `mmap` 으로 Java 힙** reserve(최대 `-Xmx`) + 메타스페이스·코드캐시. → **Java 힙은 exec가 아니라 이 단계에서 생김.**
3. **스레드 생성 시마다**: 그때그때 `mmap` 으로 스레드 스택(`-Xss`). 레이어 4a는 연결마다 이 mmap.

**reserve ≠ 물리 배정**: `mmap` 은 가상 주소만 예약. 실제 물리 페이지는 **처음 touch할 때** page fault로 붙음(demand paging). `-Xmx16g` 줘도 시작 직후 실사용은 적음. `-XX:+AlwaysPreTouch` 로 미리 touch 가능. → NMT의 **reserved vs committed** 가 이 구분.

## 7. 스택/힙 구분은 누가 하나 — 컴파일러 (syscall/런타임 아님)

**언어 규칙 + 컴파일러**가 결정. 런타임에 "스택? 힙?" 판단하는 순간도, syscall도 없다.

**javac**: 심볼에 kind(LOCAL/FIELD/STATIC)를 태그(문법적 위치로) → kind마다 정해진 opcode를 뽑음. **힙으로 보내는 대체 opcode 자체가 없음**(`new`는 정의상 힙).

| 심볼 kind | 사는 곳 | opcode |
|---|---|---|
| 지역변수/파라미터 | **스택 슬롯** | `iload/istore`, `aload/astore` |
| 인스턴스 필드 | **힙 객체 내부** | `getfield/putfield` |
| static 필드 | 클래스 저장소 | `getstatic/putstatic` |
| `new` 결과 | **힙** | `new`, `newarray` |

```java
int i = 5;              // i(값)      → 스택 슬롯
Node n = new Node();    // n(참조)     → 스택 슬롯 / Node 객체 → 힙
int[] a = new int[100]; // a(참조)     → 스택 슬롯 / 배열 → 힙
```

**JIT(C1/C2)에서만 진짜 "판단"** (여전히 syscall 무관):
- **레지스터 할당**: 많은 지역변수는 스택에도 안 가고 **CPU 레지스터**에만 삶. 모자라면 스택 spill.
- **탈출 분석(Escape Analysis) → 스칼라 치환**: `new` 객체가 메서드 밖으로 안 새면 힙 할당을 없애고 필드를 스택/레지스터로. 소스의 `new` 가 실제론 힙에 안 갈 수 있음.
- 실험: `-XX:-DoEscapeAnalysis` 끄고 JFR로 할당률 차이 관측("왜 예상보다 객체가 적지?"의 답).

## 8. 스택·힙은 여러 층에 존재 — 하드웨어 / OS / JVM

"스택·힙"은 한 곳이 아니라 여러 층위에 있고, **JVM 것은 그 위에 얹혀 있다.**

| 개념 | 하드웨어(CPU) | OS(커널) | JVM |
|---|---|---|---|
| **스택** | `RSP` 레지스터 + `PUSH/POP/CALL/RET` (ISA 내장) | 메인스택 영역 세팅·폴트 확장·가드페이지 | JVM 스택(스레드별) |
| **힙** | **없음** (그냥 LOAD/STORE) | brk/mmap 익명 메모리 | Java 힙(GC 관리) |

**핵심 관계**:
- **스택: OS 것과 JVM 것이 물리적으로 같음.** HotSpot 플랫폼 스레드는 OS 스레드와 **1:1** → Java 프레임이 진짜 OS 스레드 스택 위에 놓임. `jstack` = 이 하드웨어 스택 내용을 번역한 것.
- **힙: OS 것과 JVM 것이 분리.** Java 힙은 JVM이 mmap한 **익명 영역** — OS 눈엔 그냥 메모리, "여기 Object 몇 개"는 JVM만 앎. → 힙 분석은 OS 도구가 아니라 `jmap`(JVM 도구).

**CPU의 스택 지원 — 메커니즘만, 정책은 위층**:

| 무엇 | 누가 |
|---|---|
| RSP 이동, PUSH/POP, CALL/RET | **CPU** |
| 스택 영역 확보·확장 | **OS** |
| 프레임 레이아웃(슬롯 배치) | **컴파일러** (ABI) |
| 오버플로우 감지 | **MMU + OS** (가드페이지) |

- CPU는 "프레임"·"지역변수"를 모름. "CALL은 [RSP]에 리턴주소 넣는다"만 앎. **"스택 프레임"은 소프트웨어 약속(호출 규약/ABI).**
- **힙은 CPU 지원이 전혀 없다** — 전용 레지스터도 명령도 없음. 이유: 스택의 LIFO는 "포인터 밀고 당기기"라 하드웨어에 딱, 힙의 **임의 순서 할당·해제·GC 도달성**은 알고리즘(정책) 문제라 하드웨어로 고정 불가. **유연함의 대가 = 소프트웨어 관리 필수.**

**아름다운 반례 — Virtual Thread (Loom, JDK21)**: 가상 스레드의 스택은 OS 스택이 아니라 **Java 힙에 객체(continuation stack chunk)로 저장**. 논리적으론 스택인데 물리적으론 힙 → "스택=OS 스택"은 플랫폼 스레드일 때만 참. 이래서 가상스레드는 `-Xss` 안 먹고 수백만 개 가능. **레이어 4a(플랫폼 스레드, 폭발) ↔ 가상 스레드(힙 스택, 값쌈) 비교 소재.**

## 9. OS ↔ JVM 메모리 경계 (심화: VMA · brk/mmap/malloc · 매핑)

§6·§8을 더 파고든 내용. "Java 힙은 OS의 무슨 영역인가", "누가 힙/스택을 나누나"의 정밀한 답.

### 9.1 "OS 힙"은 두 뜻 — 혼란의 근원

| 뜻 | 가리키는 것 | Java 힙이 이거냐? |
|---|---|---|
| **좁은 뜻** | `[heap]` = **brk로 늘리는 특정 영역**(C malloc용) | ❌ 아니다 |
| **넓은 뜻** | "OS가 동적으로 내주는 메모리" 일반 | ✅ 맞다 (mmap 경로) |

→ "Java 힙 ≠ OS 힙"이라 할 땐 **좁은 뜻**([heap]/brk). 넓은 뜻으론 Java 힙도 OS가 준 동적 메모리(단 brk 아닌 mmap).

### 9.2 메모리 받는 법: brk vs mmap vs malloc

`brk`·`mmap` = **커널에서 메모리 받는 법(syscall)**. `malloc` = 그 **위에 얹힌 libc 관리자**.

| | `malloc` | `mmap` | `brk` |
|---|---|---|---|
| 정체 | libc 함수(`man 3`) | 시스템콜(`man 2`)+래퍼 | 시스템콜 |
| 층 | 높음(관리자) | 낮음(커널 직접) | 낮음 |
| 단위 | 아무 크기(바이트) | 페이지(4KB 배수) | 연속 확장 |
| 반납 | `free()` | `munmap()` | break 되돌림 |

**관계 — 도매(mmap/brk) vs 소매(malloc)**:
```
malloc(24) ─┐ 작은 요청은 자기 풀에서
            ├─ 풀 모자라면 → mmap/brk 로 커널에 도매 요청
libc malloc ┘ (glibc: 128KB↑는 malloc이라도 바로 mmap)
```
- **JVM은 malloc 우회, `mmap` 직접** — Java 힙은 GC가 독점할 **연속 전용 영역**이라야 하므로. (HotSpot `os::reserve_memory`→`mmap`)
- Windows: `mmap` 대신 `VirtualAlloc`, `malloc`은 내부 `HeapAlloc`.

### 9.3 커널의 단위 = VMA (역할 중립 생짜 메모리)

- 커널은 주소공간을 **VMA(`vm_area_struct`) 리스트**로 관리. 각 VMA = 주소범위 + 권한 + 플래그(**익명 vs 파일백드**, private/shared).
- **VMA에 "heap 타입"·"stack 타입"은 없음.** `mmap` 으로 받은 **익명 private 영역 = 역할 미정의 생짜 RAM.**
- **역할은 쓰는 방식이 정함**: GC가 객체 나눔 → 힙 / SP가 LIFO로 훑음 → 스택 / 버퍼로 씀 → 버퍼. **같은 mmap, 다른 용도.**
- "익명(anonymous)" = 파일 백킹 없음(0으로 채움, 압박 시 스왑). 힙/스택 여부와 **무관한 직교 축.**

**그래서 "구분"은 커널이 아니라 위층이 만든다** (§8 재확인): 하드웨어(RSP/CALL vs 힙 지원 전무)·컴파일러(슬롯 vs `new`)·런타임(GC/SP 규율). 커널은 exec 때 세팅한 `[heap]`(brk)·`[stack]`(메인) **둘만** 의미론적으로 라벨.

### 9.4 프로세스 주소공간의 실제 — "힙+스택"은 단순화

한 프로세스는 힙·스택 둘만이 아니라 **수십 개 영역**(대부분 mmap):
```
r-xp  /usr/bin/java        ← 코드 (파일 mmap)
rw-p  [heap]               ← brk C힙 (작음)          ┐ 커널 라벨
rw-p  (이름없음)  ★Java힙   ← private 익명 mmap       ┐
rw-p  (이름없음)  스레드스택  ← private 익명 mmap       │ 라벨 없는
rw-p  (이름없음)            ← private 익명 mmap       │ 익명 영역이
r-xp  /lib/libc.so         ← 코드 (파일 mmap)        │ 메모리의 주력
rw-p  [stack]              ← 메인 스택               ┘ 커널 라벨
```
→ **`[heap]`·`[stack]` 라벨은 딱 2줄. "스택도 [heap]도 아닌" 익명 mmap이 오히려 대부분.** Java 힙은 그중 하나이며, **커널 라벨상 [heap] 아님 / 기능상 힙 맞음**(GC가 힙처럼 씀).

### 9.5 "JVM 할당 전" OS가 힙/스택 구분하나 (타임라인 자체는 §6)

- **T0 exec**: 커널이 **네이티브** `[stack]`·`[heap]` 세팅 → **이 둘은 커널이 구분**(JVM 자신 C++이 씀).
- **T1 JVM**: Java 힙·스레드 스택을 mmap → **역할은 JVM이 부여**, 커널은 "Java 힙"을 모름(그냥 익명 VMA).
- **커널 관여 그라데이션**: 메인 `[stack]`(강함: RSP·argv·grows-down) > `[heap]` brk(중간: 예약·라벨, malloc이 관리) > 익명 mmap(없음: 유저공간이 역할 부여).

### 9.6 매핑 — JVM ↔ OS (플랫폼 스레드)

```
JVM 스택 ═══ OS 스레드 스택   (같은 바이트! -Xss가 Java 재귀깊이 정함)
Java 힙  ─⊆─ 익명 private mmap 영역   (≠ [heap]/brk. 별개 영역, 격리)
C++/JNI  ─⊆─ [heap] brk + malloc
```
- **JVM 스택 = OS 스택**: HotSpot 프레임이 네이티브 스택에 직접 얹힘.
- **Java 힙 ⊆ 익명 mmap**: OS `[heap]`과 **다른 영역**. GC 독점 위해 malloc/brk와 격리(혼용 X).

**교차 케이스 — 역할 ≠ 위치**:
- 가상 스레드(Loom): **JVM 스택**(프레임)을 **Java 힙**에 stack chunk 객체로 저장. 역할=스택, 위치=힙.
- 스칼라 치환(JIT 탈출분석): `new` 객체(**JVM 힙** 대상)를 **OS 스택**/레지스터에 realize. 역할=힙객체, 위치=OS스택.
→ 논리 역할과 물리 위치는 스레드종류·JIT가 바꾼다.

### 9.7 그림 요약

```
        커널: 생짜 메모리를 brk·mmap으로 내줌 (역할 중립)
              단 exec 때 [stack]·[heap] 2개만 자기가 라벨
                          │
   하드웨어(RSP/CALL) + 컴파일러(슬롯 vs new) + 런타임(GC/SP)
              이 "힙/스택" 구분을 강제
                          │
        JVM: 생짜 익명 mmap 하나를 받아 "Java 힙"으로 씀
             (커널 라벨상 [heap] 아님 / 기능상 힙 맞음)

  비유: 빈 창고 임대(mmap) → JVM이 선반 설치·관리(GC) → "곡물창고(힙)"
        부동산 대장(커널)엔 "임대부지"로 등록 ≠ 실제 용도(힙)
  증거: SOE(깊이) ≠ OOM(양) — 규율이 다르니 실패도 다름
```

**검증(직접)**: `cat /proc/<pid>/maps`([heap]/[stack]/익명 분리) · `pmap -x` · `jcmd VM.native_memory`(JVM 의미 라벨) · `javap -v`(프레임). Windows는 VMMap.

## 10. 실행파일 → 프로세스 시작 (ELF · exec · 섹션/세그먼트 · ABI)

"프로세스가 어떻게 시작되고 메모리가 어떻게 배치되나"를 문법 레벨과 커널 레벨로.

### 10.1 문법 레벨(C 표준) vs 커널 레벨 — 추상 vs 구현

- **C 표준(ISO C)** 은 **저장 기간(storage duration)** 만 규정 — "스택/힙/mmap"이란 단어 **없음**:
  - `automatic`(지역) / `static`(전역·리터럴) / `allocated`(malloc) / `thread`(C11).
  - **수명·의미만** 정함. "스택으로 구현"은 강제 아님(다만 모든 구현이 그럼).
  - 동적 메모리 표준 = **`malloc`/`free` 뿐. `mmap`은 ISO C 아님(POSIX).** malloc 구현은 내부에서 brk/mmap(Win: VirtualAlloc) 호출.
- **커널 레벨**은 그걸 **VMA·페이지·brk/mmap syscall·demand paging** 으로 실현.
- **컴파일러가 다리**: 문법의 저장기간 → opcode/슬롯 → 커널이 준 영역 사용.

### 10.2 실행파일 형식 — ELF / PE / Mach-O

| OS | 형식 | 확장자 |
|---|---|---|
| Windows | **PE** | `.exe`, `.dll` |
| Linux | **ELF** | 보통 없음, `.so` |
| macOS | Mach-O | 없음, `.dylib` |

- Linux는 **확장자 무시** — 매직 `0x7F454C46`(첫 4B, 뒤 3개 ASCII 'ELF') + 실행권한으로 판별.
- **`.class`/`.jar`는 ELF 아님 = JVM 바이트코드**(매직 `CAFEBABE`). OS가 실행하는 건 **ELF/PE인 `java`**, 그 JVM이 `.class`를 해석 → "OS 실행파일=java / JVM 실행대상=.class" 두 층.

### 10.3 컴파일 → 섹션, 링커 → 세그먼트

컴파일러/어셈블러가 **선언 종류로 섹션 분류**:

| 선언 | 섹션 | 백킹/권한 |
|---|---|---|
| 함수 코드 | `.text` | 파일백드 r-x |
| 리터럴·const | `.rodata` | 파일백드 r-- |
| 초기화 전역 `g=5` | `.data` | 파일백드 rw- |
| 미초기화 전역 `b` | `.bss` | **익명 0, 파일엔 크기만** |

- **`.bss` 최적화**: 0값을 파일에 안 담고 **크기만** 기록 → 파일 작게, 로드 시 0으로 채움. (그래서 `.data`와 분리)
- **섹션(section)** = 컴파일러가 만듦, **링커**가 씀(`.text`/`.data`/`.bss`). **세그먼트(segment/PT_LOAD)** = 링커가 섹션을 **권한별로 묶음**, **커널**이 exec 때 VMA로 매핑.

### 10.4 exec — 인자는 (경로·argv·envp), text/data는 파일에서

- `execve(pathname, argv, envp)` — **text/data는 인자 아님.** 커널이 **파일(ELF)의 프로그램 헤더**를 읽어 매핑.
- exec의 진짜 인자(argv/envp)는 **새 스택에** 얹힘 → `main(argc, argv)`.

### 10.5 실행 시 배치 (누가·어디서)

```
높은주소  [stack] 커널세팅·아래로자람(작게시작)
          (mmap: 공유lib=ld.so, Java힙·스레드스택=앱)  ← 실행중 추가
          [heap] brk·위로자람(빈채시작→malloc)
          .bss/.data/.rodata/.text  ← 실행파일에서 매핑
낮은주소
```
- **정적(코드·데이터)=파일에서, 스택 시작=커널, 힙·추가영역=실행되며 자람.**
- 함정: **자란다**(미리 안 뗌) · **매핑 ≠ 물리**(touch 시 붙음) · **4구역 아님**(lib·ld.so·vdso 다수).

### 10.6 ABI = 컴파일러↔OS 계약

- OS가 실행파일 읽는 **규칙 = ELF 명세 + 플랫폼 ABI**(System V AMD64 등: 호출규약·초기스택·엔트리).
- **컴파일러/링커 = 생산자**(명세대로 씀), **커널 로더 = 소비자**(명세대로 읽음). 같은 공개표준 → 서로 내부 몰라도 맞물림.
- 그래서 **PE(.exe)는 Linux에서 안 돎**(다른 계약). = JVMS·ABI·ELF 모두 같은 **경계 표준.**

### 10.7 ELF 헤더 = 바이너리 메타데이터 (바이트는 중립)

- 파일은 전부 0101 — **코드 바이트·데이터 바이트는 봐선 구분 불가.**
- **파일 앞 고정 위치·형식의 바이트(ELF 헤더)** 가 "어느 오프셋~오프셋이 .text(R+X)/.data(R+W)"를 **라벨링하는 목차.**
- 커널은 오프셋 0의 고정 헤더 → `e_phoff` → 프로그램 헤더 표대로 매핑. flags(R/X·R/W)는 런타임에 **MMU가 페이지 권한으로 강제**(코드에 쓰기=폴트).
- **바이트가 "나 메타데이터"라 말하지 않음** — **위치(오프셋0) + 약속(명세)** 이 그 역할을 부여.

### 10.8 관통 테마 — 재료는 중립, 의미는 약속

> **파일 바이트든 메모리 페이지든 그 자체는 역할이 없다. "메타데이터냐 내용이냐 / 힙이냐 스택이냐"는 위치·플래그·약속(명세/런타임)이 부여한다.**

- 메모리: 익명 영역(중립) → VMA/런타임이 힙·스택 역할.
- 파일: 바이트(중립) → ELF 명세가 헤더/.text/.data 역할.
- 같은 원리의 두 얼굴. (§7 컴파일러 분류, §9.3 VMA 중립과 이어짐)

**검증**: `file prog`·`readelf -h/-l/-S prog`·`xxd prog|head`(ELF 매직)·`size prog`.

## 11. 스레드 — 공유 vs 사설 자원 (레이어 4a 출발점)

### 11.1 무엇이 공유되고 무엇이 사설인가

| 구분 | 공유(모든 스레드) | 사설(스레드마다) |
|---|---|---|
| 메모리 | **코드·data·bss·힙(Java힙 포함)**·주소공간 전체(VMA) | **스택** |
| 실행 | — | **레지스터**(SP·PC), 실행 문맥 |
| 기타 | 파일 fd, PID, 시그널 핸들러 | TLS, 스레드 ID |

- 커널 근거: 스레드 = **같은 `mm_struct` 공유**(`clone(CLONE_VM)`) → 같은 VMA·페이지테이블. 프로세스 = 별개 mm_struct(격리).

### 11.2 스택의 "사설"은 관례다 (하드웨어 격리 아님)

- 각 스레드 스택 = **공유 주소공간 안의 VMA**(익명 mmap). **모든 스레드 스택이 같은 주소공간에 다 보임.**
- "사설"인 이유 = **각 스레드 SP가 자기 것만 가리키는 관례.** → 다른 스레드 스택 주소를 넘겨받으면 **접근 가능**(위험).
- **진짜 사설은 레지스터(SP·PC)뿐** — CPU 실행 문맥, 컨텍스트 스위치 때 저장/복원.
- 대조: **프로세스 간은 MMU 하드웨어 격리**(서로 메모리 못 봄).

### 11.3 레이어 4a·JMM 연결

| 데이터 | 공유? | 그래서 |
|---|---|---|
| KV 저장소(힙의 HashMap) | **공유** | 동시 접근 → **락 필요**(race·lost update) |
| 명령 파싱 지역변수 | 사설(스택) | 각자 스택 → **동기화 불필요** |

- **힙이 공유라서** 동시성 문제·락·`ConcurrentHashMap` 이 필요. **스택이 사설이라** 지역변수는 안전.
- JMM: 공유 힙 → **가시성**(`volatile`/`synchronized`, happens-before) / 사설 스택 → 가시성 문제 없음.

## 12. 이 프로젝트에서 어디에 물리나 (적용)

| 데이터 | 위치 | 왜 |
|---|---|---|
| KV 저장소 전체(HashMap·String·Node) | **힙** | DB 켜진 내내 기억, 명령 흐름 초월, 스레드 공유 → 스택 불가 |
| 명령 파싱 임시 토큰·인덱스 | 스택(일부 레지스터) | 그 명령 도는 동안만 → LIFO 딱 맞음, 빠름 |
| 트리(레이어 6) 재귀 순회 | 스택 프레임 | 깊이 폭발 시 SOE 주의 |
| WAL/NIO 버퍼(레이어 2/4b) | **direct(off-heap)** | 힙 우회, 안 풀면 native OOM → NMT |

**관측 매핑**: 힙 내부 = `jmap -histo`(JVM만 앎) / OS가 아는 reserved·committed = `jcmd VM.native_memory`(NMT) → **같은 힙을 다른 층위에서** 봄. 콜스택(하드웨어 스택) = `jstack`. GC/힙 추이 = `jstat -gc`.

## 요약 (한 줄씩)

1. **스택 = 흐름에 묶인 임시공간(LIFO), 힙 = 흐름과 무관하게 기억할 데이터.** 서로의 약점을 메우는 분업.
2. **프레임 = 함수 호출 한 번의 작업공간.** 스택은 프레임 더미 = 호출 경로. `jstack` 한 줄 = 프레임 하나.
3. **SOE = 깊이 초과**(논리 경계, 스왑 무관, 즉시). Java에선 사실상 재귀만. C와 달리 프레임 크기론 안 터짐.
4. **OOM = 양 초과**, 영역별로 메시지가 다름. 힙(`-Xmx`↑) vs 네이티브(`-Xmx`↓, NMT).
5. **SOE·OOM은 JVM이 던진다. OOM Killer는 커널이 프로세스를 즉살**(Java 에러 아님, 컨테이너 함정).
6. **개별 할당은 syscall 아님**(SP 이동 / TLAB bump). syscall은 영역 확보·확장 때만(mmap/VirtualAlloc). reserve ≠ 물리 배정(touch 시 붙음).
7. **스택/힙 구분은 컴파일타임 결정**(심볼 kind → opcode). 진짜 판단은 JIT(레지스터 할당·탈출 분석).
8. **스택·힙은 CPU/OS/JVM 여러 층에 존재.** Java 스택 = OS 스택(1:1), Java 힙 = OS가 준 익명영역을 JVM이 독자관리. CPU는 스택만 지원(힙은 순수 소프트웨어). 가상스레드는 스택마저 힙에 둠.
9. **커널 단위 = VMA(역할 중립 생짜 메모리).** "힙/스택 타입"은 VMA에 없음 — 역할은 쓰는 방식(GC=힙 / SP LIFO=스택)이 정함. 커널은 exec 때 `[heap]`(brk)·`[stack]`(메인) 둘만 라벨.
10. **`mmap`/`brk` = 커널에서 받는 법(도매), `malloc` = 그 위 libc 관리자(소매).** JVM은 GC 독점 위해 malloc 우회하고 `mmap` 직접(Windows `VirtualAlloc`).
11. **Java 힙 = 익명 private mmap 영역** — 커널 `[heap]`(brk)도 스택도 아님(별개·격리), **기능상은 힙**. 매핑은 고정 아님: 가상스레드(스택→힙)·스칼라치환(힙→OS스택)이 역할/위치를 가른다.
12. **C 표준은 저장기간(추상)만, 힙/스택/mmap 없음** — 동적메모리는 malloc뿐(mmap은 POSIX). 실현은 커널(VMA·페이지)이, 다리는 컴파일러가.
13. **실행파일(ELF/PE) = 바이너리 + 헤더(메타데이터).** 컴파일러가 섹션(.text/.data/.bss)으로, 링커가 세그먼트로, 커널이 exec 때 매핑. `.bss`는 크기만(파일 절약). ABI = 컴파일러↔OS 계약.
14. **바이트·페이지는 중립, 의미는 위치·플래그·약속이 부여** — ELF 헤더가 .text/.data를, VMA/런타임이 힙/스택을. 파일과 메모리의 같은 원리.
15. **스레드: 코드·data·힙·fd·주소공간 공유 / 스택·레지스터·TLS 사설**(같은 mm_struct). 스택 사설은 관례(SP), 진짜 사설은 레지스터뿐. **힙 공유→락 필요, 스택 사설→지역변수 안전**(레이어 4a).
